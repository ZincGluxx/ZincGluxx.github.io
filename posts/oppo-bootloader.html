拿到 root，
为什么仍解不开锁？

从 OPPO Find X8s 与 Pad 5 的两份研究记录出发，重新看 Android 启动链里的三道门。

我在 GitHub 上整理过两份设备解锁记录：一份针对 OPPO Find X8s，另一份针对 OPPO Pad 5。如果只看操作表面，它们像是两套相似的刷机流程；往下一层看，真正有意思的是一个问题：为什么已经拿到系统里的最高权限，设备仍然不能直接解锁 Bootloader？

这篇文章不复述命令清单。仓库 README 已经记录了特定版本下的尝试路径；这里更想把它们放回 Android 的安全模型里，解释每一步究竟跨过了哪一道边界，又有哪些结论不能轻易外推到别的设备。

01 · 系统里有三道不同的门

日常说的“解锁”很容易把三个状态混在一起。第一道门是运行中的 Android 系统权限：root 让进程以更高权限访问当前系统。第二道门是引导器提供的 Fastboot 接口：电脑要与引导器对话，设备得先进入相应模式。第三道门才是Bootloader 的锁状态：它决定设备是否允许刷入非官方镜像，以及验证启动如何对待这些镜像。

这三个状态相关，却不能互相替代。AOSP 的引导器解锁文档明确区分了进入 bootloader 模式与执行解锁；设备还应检查是否允许解锁，并在用户物理确认后清除数据。因此，root shell 不等于 Bootloader 已解锁；看到“fastboot mode”也不等于解锁命令一定会被接受。

从系统权限走到可刷写状态，并非一次“提权”，而是连续跨越系统、引导器与设备信任状态的边界。

这正是两份仓库记录的共同主线：先在特定旧版本中取得系统内的高权限，再处理引导器入口，最后才尝试改变锁状态。它也解释了为什么单独下载一个 root 工具，通常并不能回答“这台 OPPO 设备能否解锁”的问题。

02 · A/B 槽位为什么关键

Android 的 A/B 更新把一部分可启动分区分成当前槽位与备用槽位。系统运行时，更新通常为下一次启动准备另一组镜像；新槽位启动失败，设备有机会回到旧槽位。这个设计首先服务于更新的可靠性，而不是为改机预留后门。AOSP 对无缝更新和槽位实现都有详细说明。

在我的两份记录中，关键动作都落在“另一槽位的 lk 镜像”上：不是在当前系统里直接宣布解锁，而是让下一次启动走到一个能提供 Fastboot 入口的引导阶段。Find X8s 记录和Pad 5 记录都特别强调槽位与固件版本的对应关系。

但“有 A/B 槽位”绝不意味着“任意设备都能这样做”。Android 的验证启动把信任链从硬件根延伸到引导器和系统分区，还存在防回滚机制。能否写入、写入后能否被引导器接受、能否进入可用的 Fastboot，以及最终是否允许解锁，分别取决于设备实现和固件状态。把某个版本上的现象直接推广到同芯片的另一款机器，是最容易出错的一步。

03 · 同一思路，两种设备条件

两份 README 的目标版本并不相同。Find X8s 记录针对 ColorOS 15.0.1.610，描述了借助 preload.so 获取临时高权限、随后尽快完成引导阶段操作的路径；Pad 5 记录针对 ColorOS 16.0.9.400，描述了 GhostLock 与 KernelSU 参与的另一条路径。它们共有的是“先解决系统权限，再处理备用槽位的引导器入口”，不同的是取得权限的条件、时间窗口与固件依赖。

记录明确写出的目标环境最需要避免的误读
Find X8sColorOS 15.0.1.610；临时权限窗口一次成功路径不代表新系统版本也适用
Pad 5OPD2506；ColorOS 16.0.9.400同名平板的不同型号、地区固件不能直接等同

两份 README 把处理器简称为“天玑 9400”，而 OPPO 官方的Find X8s 参数页与平板产品页标注的是天玑 9400+。写技术记录时，这类“差一个加号”的细节值得纠正：芯片家族相近，不等于引导器镜像、分区布局或安全补丁状态相同。

04 · 漏洞编号能说明什么

两个仓库都提到了 CVE-2026-43499。Linux 内核 CVE 记录将它描述为 rtmutex 的 remove_waiter() 在代理锁回滚路径上错误地使用当前任务，可能留下悬空的等待者状态；这属于内核层面的漏洞，而不是“天玑 9400+ 专属开关”。可核对的原始描述见Linux 内核 CVE 记录。

这里必须把“漏洞存在”与“某台设备可用某个工具稳定提权”分开。CVE 页面证明的是上游问题及其修复背景，不能单独证明某个 OPPO 固件包含可利用的实现，也不能替代具体构建号、内核补丁和设备日志。我的仓库提供的是面向指定版本的实践记录；它们不是所有 Find X8s、Pad 5 或所有 ColorOS 版本的兼容性认证。

05 · 解锁之后，控制权意味着什么

研究启动链并不只是为了得到一个“已解锁”的状态字。设备所有权还体现在使用者能否研究系统行为、验证自己的假设、修改功能边界。我另一个项目长续航解锁就是具体例子：它研究 ColorOS 的 MediaTurbo 如何维护“视频长续航模式”的应用支持列表，并用 LSPosed 模块让用户自己选择应用。项目 README 只声称在 Find X8s 的特定 ColorOS 16 环境中实测；其他版本仍需重新核验类名和策略实现。

这与 Bootloader 解锁不是同一个技术问题，却回答了“为什么有人在意控制权”。另一方面，锁定状态与验证启动也确实保护数据与系统完整性。让用户拥有更多修改能力，通常也意味着用户要亲自承担来源验证、备份与恢复的责任。这两点都是真实的，不必把安全与自由写成简单的二选一。

06 · 比成功截图更重要的边界

如果未来继续整理这类记录，我更希望每篇都能回答四个问题：具体是哪台设备、哪一版固件、哪一个补丁状态、有哪些可核查的结果？二进制镜像最好保留来源与校验值；临时权限和最终锁状态应分别记录；失败、重启、数据清除和回退条件也应如实写出。这样，读者看到的是可审视的实验条件，而不是一串看似通用的命令。

尤其要记住，AOSP 指出 Bootloader 状态变化会触发用户确认与数据清除；防回滚也可能让“刷回旧版本”并不像字面上那么简单。备份不是文章末尾的例行提醒，而是这类实验能否负责任地开始的前提。本文也不应被当作跨版本刷机指南：一旦设备、固件或镜像来源与记录不一致，就应重新验证，而不是凭经验猜测。

回过头看，两份 OPPO 仓库真正值得留下的，不只是一条可操作的路径。它们把 Android 设备上的控制权拆成了几个可以讨论的层次：运行时权限、引导入口、持久锁状态，以及验证启动的信任链。理解这些层次之后，“拿到 root，为什么仍解不开锁”就不再是反常现象，而是整个系统设计的自然结果。
