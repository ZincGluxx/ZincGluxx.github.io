OPPO Find X8s
与 Pad 5 解锁原理

内核提权、A/B 槽位、LK、Fastboot 和 Bootloader 锁状态如何串成一条链。

Find X8s 和 Pad 5 两份仓库记录的手段有所不同，但目标路径相同：在正在运行的 Android 中取得足够的写入权限，改变下一次启动使用的引导器镜像，让设备进入 Bootloader Fastboot，最后由引导器处理解锁请求。这里有三个独立问题：能否改写镜像、能否进入 Fastboot、引导器是否允许把锁状态改为 unlocked。解决前一个问题不自动解决后一个问题。

一、先分清三种权限与状态

把启动顺序压缩成一行，大致是早期引导组件 → LK 等引导阶段 → Android 内核 → 用户空间进程。实际设备还有厂商实现的验证阶段，但先后关系足以说明关键点：root 出现在 Android 已运行之后；Bootloader 的模式和锁状态却在更早的启动阶段被处理。AOSP 的引导器概览也把引导器描述为装载内核并传递启动参数的组件。

root 是运行时的 Linux 权限。一个进程在 Android 系统启动后获得 UID 0，可以执行比普通应用更多的系统操作；它并不会自动修改设备重启前由引导器读取的锁状态。系统还有 SELinux、只读分区与硬件信任链等约束，因此“拿到 root”也不应被简化成“任何分区都能无条件刷写”。

Fastboot 是引导阶段的通信接口。AOSP 区分在 Bootloader 中运行的 Fastboot 和在用户空间运行的 fastbootd；两份仓库要得到的是前者：设备重启后停在能够与电脑 Fastboot 客户端通信的引导器模式。能看到该模式，只说明入口可达。

locked / unlocked 是持久的设备状态。按 Android Verified Boot 的设备状态说明，锁定设备应验证所启动软件的来源；解锁状态允许不同的刷写和启动行为。AOSP 的解锁规范还要求设备在接受解锁命令前检查解锁许可，并由用户在设备上确认，状态转换时清除用户数据。所以“root 成功”“显示 fastboot mode”“最终显示 unlocked”必须分别验证。

二、内核提权解决了什么

正常情况下，锁定设备不应允许普通应用改写关键引导组件。两份仓库首先争取的不是解锁标志，而是在当前系统内写入指定块设备的能力。这一步为后续替换另一槽位的 lk.img 创造条件。它发生在 Android 已经启动之后；只要引导器状态还没改变，下一次启动仍要面对引导阶段的检查。

Find X8s 记录针对 ColorOS 15.0.1.610，使用 preload.so 路径取得临时高权限，并描述了 SELinux 状态变化及很短的操作窗口。LD_PRELOAD 在这里是把共享库加载进目标进程的方式；具体如何从该进程触发内核漏洞，仓库没有提供可读的利用源码或逐步分析，不能仅凭文件名推断完整实现。

Pad 5 记录针对 OPD2506、ColorOS 16.0.9.400，使用 GhostLock 应用并配合 KernelSU 维持 root。两条路径的共同点是获得足够权限去处理引导分区；“临时权限”与“持久化 root”则是不同的运行时条件，不能相互替换。

仓库都提到 CVE-2026-43499。Linux 内核 CVE 公告描述的是 rtmutex 的 remove_waiter()：代理锁回滚时，代码误用当前任务而非真正的等待任务，使后者的 pi_blocked_on 可能留下悬空引用。它解释了漏洞类别与潜在提权入口，却不能单独证明某个 OPPO 固件一定可利用，也不能证明仓库中的二进制具体怎样使用了它。

三、为什么是另一槽位的 LK

A/B 更新会为部分启动分区维护 _a、_b 两个槽位。设备从当前槽位运行时，更新系统通常把下一版写入非活动槽，准备好后再切换启动目标。AOSP 的 A/B 更新说明明确描述了 update_engine 写入备用槽，以及引导器根据槽位状态选择下一次启动目标的过程。这个机制解释了仓库为什么反复强调“当前槽位”和“相反槽位”：写错位置，改动就不会按预期在下一次启动生效，甚至可能损坏当前可启动路径。

两份仓库都附带或指向一个修改版 lk.img，并记录了把它放进非活动槽位、随后通过本地更新流程切槽的路径。LK 是引导阶段的组件，位于 Android 内核启动之前；在这条路径中，它承担的是让目标版本的设备出现 Bootloader Fastboot 入口这一环。上游 Little Kernel 项目能帮助理解 LK 所处的层级，但不能当作 OPPO 实际二进制的源码。它更不是“刷入后锁标志自动变成 unlocked”的同义词。

这里要区分仓库观察到的行为和尚未公开的补丁细节：两个仓库提供的是二进制镜像与操作记录，没有发布原厂 LK、修改后 LK 的逐字节差异或对应源代码。因此可以根据记录说“换用该镜像后出现了 Fastboot 入口”，却不能严谨地断言具体改了哪一个条件分支、验证检查或 USB 命令表。

另外，A/B 不是绕过 Android Verified Boot 的通用办法。验证启动要求从硬件信任根逐级验证后续组件；防回滚也可能拒绝较旧镜像。设备是否允许当前系统写入 lk、写入后是否接受该镜像、切槽是否成功，都是固件和设备实现相关的前提。

四、Fastboot 入口与最终解锁

切槽后若设备显示仓库所述的 fastboot mode，机制链只走到了第四步。此时电脑可以向引导器发起解锁请求，但是否接受请求由引导器决定。AOSP 把 get_unlock_ability 作为解锁许可条件，并要求在设备上进行物理确认；解锁操作会清除用户数据。这也是为什么不能把“Fastboot 可用”当成“Bootloader 已解锁”。

两份 README 的最后一步都记录了通过 Fastboot 发起解锁，并在设备上用按键确认。要验证结果，应该读取设备实际报告的锁状态，而不是只看命令发出或界面曾出现。若许可条件、设备实现或验证链不满足要求，进入 Fastboot 后仍可能被拒绝。

处理器型号不应被用来代替固件匹配条件。OPPO 官方的 Find X8s 参数页和平板产品页都标为天玑 9400+；仓库 README 中的“天玑 9400”是简写。即使 SoC 同属一个系列，两机的 LK 镜像也不能因此视为可互换，目标版本号更不能省略。

六、哪些细节尚不能确认

从现有公开材料可以重建权限获取 → 写入非活动槽位 LK → 切槽 → Bootloader Fastboot → 解锁请求这条流程，但不能进一步声称：某个 LK 镜像具体修改了哪些指令；所有同型号设备都允许写入关键分区；某个安全补丁版本仍受该 CVE 影响；或任何拿到 root 的设备都能复用这套方法。要回答这些问题，需要原始镜像与补丁差异、内核构建信息、设备日志，以及解锁前后的状态输出。

这篇文章解释的是两份仓库记录的原理，不是跨版本刷机步骤。实际风险集中在错误的槽位、错误的镜像、失败的启动验证和解锁时的数据清除。尤其是防回滚与 A/B 回退并不等价：备用槽位还在，也不保证旧版本始终能启动。
