吉林大学校园网认证协议
逆向与实现

从抓包无门到逐字节复现：Dr.COM 私有协议的四阶段拆解、登录帧的完整解剖，以及把「能认证」做成「是软件」的工程思路。

本文基于我实际完成的一个开源项目展开：用 Rust 从零重写吉林大学 Dr.COM 校园网认证客户端（ZincGluxx/drcom-rs），协议基准与大量参考实现来自社区项目 jlu-drcom-client。文中所有十六进制示例均取自测试向量（占位账号 testuser），不含任何真实凭据。

阅读顺序
  1. 背景：我们在和什么协议打交道
  2. 逆向的起点：站在四代社区实现上
  3. 认证流程详解

一、背景：我们在和什么协议打交道

吉大校园网用的是城市热点 Dr.COM 认证系统。它的位置在 802.1X 之后：机器插上网线能拿到 IP（校园内网可达），但要出外网必须通过 Dr.COM 网关的认证——客户端与认证服务器之间走一套基于 UDP 的私有二进制协议，官方客户端是闭源 Windows 程序（核心逻辑在 DrAuthSvr.dll 里，还被加壳保护）。

这套协议的几个基本事实：

  • 认证服务器：UDP 10.100.61.3:61440（本地端口也固定绑 61440，靠 SO_REUSEADDR 共存）；
  • 协议分四个阶段：挑战（challenge）→ 登录（login）→ 保活（keep-alive）→ 登出（logout）；
  • 报文都是短二进制帧，字段靠偏移定位，没有 TLV、没有版本协商头——相当「上古」；
  • 服务器在线状态以 IP + MAC 为键，同一时刻同一账号只能有一个客户端在线。

官方客户端的问题：闭源、无诊断能力、出问题只给一句模糊提示。于是就有了社区的三次「重新发明」，以及我的第四次——把它做成一个 6.5 MB、内存 24 MiB、带完整诊断的 Rust 原生程序。

二、逆向的起点：站在四代社区实现上

从零抓包逆向是被 VMP 壳挡死的（原版 protocol.rs 的 328 字节变体我至今没能拿到实际报文）。真正可行的路径是逐字节对齐社区参考实现：

世代实现价值
A老版 C/C++ 客户端泄漏源码协议结构最原始的出处
BPython newclient.py / jlu-drcom-py3本部署实际认证成功过的实现，我的逐字节基准
CJava 重写（2017 官方抓包）提供官方对照向量与「正确」校验和写法
D安卓移植版本协商字段的交叉验证

关键决策：照抄 B 世代，哪怕它看起来是错的。最有名的例子是校验和：Python 用 re.findall(b'....', s) 分组，而正则的 . 不匹配 0x0a（换行字节），遇到含 0x0a 的窗口会错位一个字节，导致后面的分组整体偏移。Java 重写「修正」了这一点——但我实测发现，服务端根本不校验这个和（C# 移植用正确算法照样认证成功）。结论：照抄 Python 的错误版本，同时把两个版本的结果都钉进测试，防止后人手痒「修正」之后悄悄改变线上行为。

这是逆向工程里很重要的一课：兼容性优先于正确性。你的目标不是写出教科书代码，而是复现一个正在运行的服务所期待的字节序列。

三、认证流程详解

3.1 挑战（Challenge）：20 字节的敲门砖

客户端发 20 字节：

01 02 ec f0 10 00 | <nonce:2> | <本机 IP:4> | 00 00 00 00 ...
  • 首字节 01 是操作码，02 是子码；
  • nonce 取 Unix 秒的低 16 位（原版客户端调 C 运行时的 time()；社区 Python 版则用 Unix % 0xffff，两者在绝大多数时刻等价，但模数不同——这属于要在向量里钉死的细节）；
  • 服务器回 56 字节，02 开头，关键载荷是 4 字节 salt 和序号，后续登录帧的所有 MD5 都要掺这个 salt。

挑战阶段还有个容易忽略的陷阱：服务器会记录挑战的来源 IP，后续状态校验都以此为基准。UDP socket 绑哪个本地 IP，登录帧里就得填哪个 IP，否则就是「来自陌生地址的登录」。

3.2 登录帧：368～374 字节的完整解剖

登录帧是整个协议最复杂的部分。以下按偏移铺开（以 8 字节密码的 368 字节为基准）：

偏移内容说明
003 01 00 + 账号长度+20操作码与长度前缀
4md51 = MD5(03 01 ‖ salt ‖ password)复用率最高的摘要：MAC 掩码、每个保活包都要用
20账号，固定 36 字节零填充超长账号会被拒绝而不是截断（长度字节才是真实长度）
58MAC ⊕ md51[..6]MAC 不是明文传输
64md52 = MD5(01 ‖ password ‖ salt ‖ 00 00 00 00)
80IP 数(01)、主机 IP、三个空槽地址四元组
97md53 = MD5(帧前 97 字节 ‖ 14 00 07 0b) 取前 8 字节帧内自校验
110主机名，32 字节填充
142主 DNS、DHCP、备 DNS
162OS 指纹 29 字节 + 55 零字节 + 40 字节 client key3dc79f52…be7b1，逐字手抄极易错一位
310认证版本、00、密码长度
314旋转密码块：每字节 XOR md51 对应位再循环左移 3 位长度 = 密码长度
末尾02 0c、校验和、00 00、MAC、零填充 len/4 字节、60 a2、28 零字节

最重要的工程事实：登录帧长度不是常数。两个变量决定它：

  1. 旋转密码块随密码逐字节增长；
  2. 60 a2 前的零填充是 password.len() / 4 字节（且密码恰好 16 字节时跳过——原版用了浮点除法的巧合）。

所以「368 字节的登录包」只是 8 字符密码那一组向量的特例：

密码  8 字节 → 368    10 字节 → 370（2026-09-15 对真实服务器实测）
密码 12 字节 → 373    16 字节 → 374（跳过填充）

我最初的实现就栽在这：把 368 当常数，8 位密码测试全绿，一到真实账号（10 位密码）就发错帧。修复后把 370 这个实测值直接钉进测试——不是重新推导，而是防止它再次被「简化」。

3.3 保活：40 字节的持续对话

登录成功后，每 20 秒发一个 40 字节的 0x07 包：

07 <序号> 28 00 0b <类型> <版本/标记> <nonce:2> <6 零> <4 字节尾> <校验和槽> <本机 IP> <8 零>

三个值得单独说的细节：

  • 三种形态：extra（0f 27 标记，开启一轮保活，每 10 轮重复一次）、data1、data3（携带本机 IP 与折叠校验和，data[0..24] ‖ IP 参与折叠后写回）。重发时绝不能带 0f 27——参考客户端的重发一律用协商后的版本。
  • 版本协商是跳变过程：服务器回包偏移 28..30 带一对版本字节，客户端下个包就改用新值，再被推回 0000——日志里会出现「保活版本 0000 改为 dc02 又改回 0000」的乒乓。这是正常现象，不是 bug；Python 版硬编码 dc02，Java 版读回包，我的实现取回包。
  • 07 .. 10 是推送不是应答：服务器借保活通道推消息（登录后第一条往往就是 This Program can not run in …），两个参考实现都把它当重发提示——重发同一包、计数器递增。

3.4 登出与错误码：错误是服务器说的

登出是 06 开头的帧，结构类似登录但更短。所有人类可读的失败原因都来自服务器返回的错误码，客户端只负责显示。最典型的是：

错误码 21：ldap auth error

这是 Dr.COM 服务器把账号密码转交学校统一身份系统（LDAP）校验后得到的结论——意味着挑战成功、报文解析正常，卡在最后一步的账号校验。常见原因：密码与统一身份系统不一致、账号被锁、或后端抽风。诊断时要分清层次：协议层成功 ≠ 账号层通过。

另一个反直觉的现象：LDAP 报错期间网络探针依然可达。因为网关对旧会话的授权有迟滞——登录被拒不影响已放行的 IP/MAC，直到服务器侧超时。「能上网」不等于「认证正常」，这句话值得写进每一个认证客户端的 UI。

四、从协议到软件：工程思路

4.1 参考向量是生命线

协议实现最大的风险不是「写错」，而是「改对」——某次重构顺手把错误校验和改对了，线上立刻全挂。我的做法：

  1. 向量文件（reference/）：固定 salt、占位账号、多种密码长度、特殊 MAC（最高位为 0 时 dump() 只输出两字节！），全部以十六进制字面量固化，禁止重新推导；
  2. 测试矩阵：密码 8/10/12/16 字节各一组、36 字节满长账号、短 MAC——登录帧长度、填充、旋转块全部由断言钉住；
  3. 生成脚本与校验脚本并存：gen_vectors.py 生成、verify_reference_source.py 直接读参考实现的源码重新核对，防止向量本身抄错。

4.2 架构：把「能认证」和「是软件」分开

transport.rs   UDP 收发（SO_REUSEADDR、瞬态 ICMP 错误重试）
auth.rs        挑战/登录/登出的原始状态机
keepalive.rs   保活协商与推送处理
session.rs     面向应用的会话层（事件流：阶段变化/错误/推送）
adapter.rs     网卡枚举与地址选择
config.rs      INI 解析（带错误行号）
preferences.rs DPAPI 加密的凭据持久化
event_log.rs   256 KiB 轮转日志
ui_backend.rs  GUI 与会话层的桥
diagnostics.rs 双栈体检、诊断导出

两个值得展开的传输层细节：

  • SO_REUSEADDR 必须显式设置：原版客户端和官方 DrAuthSvr.dll 都固定绑 61440，不加这个，任何残留的 Dr.COM 组件占着端口时你的 bind 直接失败；
  • Windows 会把陈旧 ICMP 错误误报给当前调用：同一 socket 上先前数据包触发的 ICMP port-unreachable，会让下一次 sendto/recv 抛 ConnectionReset——它不代表当前操作失败，必须当瞬态错误重试，否则用户会看到莫名的「首次发送失败」。

4.3 技术选型：Rust + Slint 的实际收益

同类可用方案是 C# + Avalonia（NativeAOT）。同一台机器实测：

指标Rust + SlintC# + Avalonia
安装包6.53 MB11.57 MB
应用本体13.31 MB32.77 MB
工作集内存23.8 MiB47.9 MiB
线程411

体积差几乎全部来自 Avalonia 捆绑的原生绘图栈（SkiaSharp + libGLESv2 + HarfBuzz ≈ 18 MB）；Slint 用纯 Rust 渲染器。对一个 7×24 小时挂机保活的常驻工具，这个差距有实际意义——虽然两边待机 CPU 都是 0。

选型上的教训同样值钱：Slint 布局里 height: 等于同时设 min 和 max，而 HorizontalLayout 跨轴对齐默认是 stretch，固定高度的子项会被钉在行顶——「连接按钮歪了」就是这么来的。另外它的 Windows 托盘后端一个进程只挂一个图标，用户抱怨「多个托盘图标」时先查是不是起了多个进程。

4.4 Windows 集成三件套

  • 单实例：命名互斥体 + 命名事件。重复启动时唤醒已运行实例把窗口弹出来，而不是弹第二个图标。claim() 必须在创建托盘之前。
  • 托盘语义：Slint 默认关闭窗口是 hide——正好利用它实现「关闭到托盘」；只有托盘菜单的退出才真正 NIM_DELETE。强杀进程会留幽灵图标（explorer 划过才消失）。
  • 凭据存储：CryptProtectData（DPAPI）加密落盘，绑定当前用户。自动登录依赖它，但也埋了本文第四节那个坑：自动登录会用保存的旧密码反复撞 LDAP。

4.5 诊断设计：让用户自己就能排障

一个认证工具 80% 的支持成本在「到底哪里不通」。所以把诊断做成一等公民：

  • 三层探测：校内（www.jlu.edu.cn）→ 公网 IPv4 → 公网 IPv6；全部用 TCP connect 而非 ping——境外地址 ICMP 通而 443 被丢，ping 会给出完全相反的结论；
  • 探测目标必须国内可达：1.1.1.1、[2606:4700::1111] 在国内本就超时，拿它们测「IPv6 是否正常」是我犯过的真实错误；
  • IPv6 摘要不混列 fe80::：链路本地地址存在不代表双栈可用，只统计全局地址（2001:da8::/32 = CERNET2）；
  • 事件日志全程记录：挑战 salt、报文长度、每个错误码。上面 LDAP 案例的结论（「协议层成功、账号层被拒、旧会话余温还在」）就是日志里三行还原出来的。

五、写在最后

这个项目最终形态：6.53 MB 安装包、93 项测试、连续 7.5 小时保活零失败、全套 AGPL-3.0 开源。

回头看，逆向这类「上古私有协议」的完整方法论可以压缩成四句话：

  1. 找正在运行的同协议实现，逐字节对齐它——哪怕它有 bug；
  2. 把所有「实测到的意外」钉进向量，帧长、跳变、异常 MAC 都是；
  3. 分层：协议状态机、平台集成、UI 各自独立，向量测试只保护最底层；
  4. 诊断优先：认证类软件的 UX 就是你能不能回答「我现在为什么上不了网」。
